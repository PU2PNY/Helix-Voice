# Helix Voice — Clean-Room Development Policy

## Purpose

This document is a mandatory engineering rule for Helix Voice Engine (HVE) and any future Helix Voice Codec (HVC).

Helix is developed independently. The project may implement public interoperability requirements, but it must not reproduce proprietary codec implementations, firmware, private tables, confidential documentation, trade secrets, or closed-source algorithms.

This policy is technical process documentation, not legal advice.

## Core rule

**Describe the observable requirement. Implement a new solution. Do not copy the hidden implementation.**

Examples of acceptable requirements:

- a public protocol transports a frame at a documented interval;
- an external licensed device accepts or returns a documented packet;
- a public protocol specification defines a field, size, timing rule, or network behavior;
- a codec published under a compatible open-source license exposes a documented API.

Examples that are not acceptable inputs to Helix core development:

- proprietary source code obtained without permission;
- decompiled proprietary firmware;
- extracted private lookup tables;
- confidential manuals;
- leaked SDK material;
- code copied from a repository without a clear compatible license;
- prompts containing proprietary source code and asking an AI to rewrite it;
- reverse engineering whose purpose is to recreate the internal implementation of a proprietary vocoder.

## Separation of roles

The project separates three concerns:

1. **Public interoperability specification** — observable, documented requirements.
2. **Helix implementation** — original code and DSP developed from those requirements.
3. **Legacy proprietary codec access** — external licensed hardware/software adapter when legally required.

The Helix core must remain functional without any proprietary codec backend.

## Source provenance

Every external technical source that materially influences an implementation decision should be recorded in documentation or the relevant issue/commit.

For third-party code, record at minimum:

- project name;
- upstream URL;
- exact version/tag/commit;
- license;
- files or APIs used;
- reason for use.

Do not vendor or copy code with unknown licensing.

## AI-assisted development

AI tools may be used to write Helix code only when the prompt and context do not contain unauthorized proprietary implementation material.

AI-generated code is reviewed like human-generated code. A statement that code was generated by AI does not establish clean-room provenance.

Contributors must reject generated output that appears to reproduce suspiciously specific proprietary tables, constants, firmware structures, or source patterns without a documented public source.

## Legacy codec boundary

If a legacy network requires a proprietary codec, Helix may communicate with an independently installed and appropriately authorized/licensed backend.

Such support must be implemented as an adapter boundary.

The adapter must not cause proprietary codec implementation code to enter:

- helix-core;
- helix-dsp;
- HVC;
- test vectors distributed without permission.

## Public protocol compatibility

Implementing a publicly documented protocol interface is distinct from reproducing a proprietary codec implementation.

Protocol adapters should contain only what is required for interoperability and should cite the public specification or other lawful public source used.

## Test material

Audio corpora and test vectors must have documented redistribution rights or be generated specifically for Helix.

Do not commit captured copyrighted/proprietary codec vectors unless redistribution is explicitly permitted.

Synthetic PCM vectors are preferred for unit tests.

## Pull-request checklist

Before merging code that touches codecs, protocol adapters, DSP, firmware interfaces, or interoperability:

- [ ] Source/provenance documented.
- [ ] License verified.
- [ ] No proprietary implementation code copied.
- [ ] No firmware dump or confidential document used as source.
- [ ] Tests use redistributable data.
- [ ] New dependency documented in THIRD_PARTY.md.
- [ ] Clean-room boundary remains intact.
- [ ] A rollback path exists for integration changes.

## Trademark statement

Names of third-party products or codecs may be mentioned only to identify interoperability requirements. Such references do not imply affiliation, endorsement, ownership, or inclusion of that technology in Helix.

## Escalation

If provenance or licensing is uncertain, do not merge the code. Record the uncertainty and seek qualified legal review when required.


## Patent / FTO boundary

Clean-room e autoria independente não são suficientes, por si só, para provar liberdade de operação.

Antes de implementar uma função tecnicamente próxima de uma área patenteada:
- seguir PATENT_GUARDRAILS.md;
- pesquisar claims, famílias, jurisdições e status aparente;
- produzir mapa do que evitar;
- criar design-around independente;
- documentar por que a solução Helix é tecnicamente distinta;
- bloquear produção quando o risco técnico permanecer UNCERTAIN/BLOCKED.

Patentes públicas podem ser consultadas para identificar limites legais/técnicos e estado da técnica, mas embodiments, tabelas, pseudocódigo, constantes ou detalhes específicos não devem ser usados como receita de implementação.

Sempre que possível, a pessoa/IA que analisa claims entrega ao implementador apenas:
- requisito público;
- restrições a evitar;
- fontes de domínio público permitidas;
- critérios de benchmark.

A implementação deve nascer de princípios públicos de engenharia, literatura científica, standards públicos, experimentos próprios e código com licença compatível.

Objetivos de eficiência — CPU, memória, latência, binário, largura de banda e energia — devem ser medidos. Independência de IP tem prioridade sobre ganho de desempenho.
